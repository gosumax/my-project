# Новая архитектура PARSER PD

## 1. Главный принцип

Строим парсер так, чтобы одна и та же архитектура могла работать:

* с записанным видео;
* в будущем с realtime-видеопотоком.

Поэтому не привязываем основную логику к MP4.

Основной поток:

```text
VIDEO / REALTIME
       ↓
9 TABLES
       ↓
TABLE PIPELINES × 9
       ↓
YOLO detection / segmentation
       ↓
OpenCV tracking
       ↓
только изменившиеся ROI
       ↓
OCR / PARSeq / Card recognition
       ↓
события
       ↓
нормализация
       ↓
HAND STATE
       ↓
Excel / DB
```

---

# 2. Разделение видео на 9 столов

Вход:

```text
одно видео PokerDom
```

На первом этапе:

```text
VIDEO
 ↓
TABLE 1
TABLE 2
TABLE 3
...
TABLE 9
```

Каждый стол после разделения должен иметь собственный pipeline.

Важно: дальше вся логика должна работать одинаково для одного стола, независимо от того, был ли источник MP4 или realtime.

---

# 3. YOLO используется не только для общего ROI

Ключевая идея:

**YOLO не должен читать текст.**

YOLO должен определять, **что где находится**.

Есть два уровня использования YOLO.

### Уровень 1 — поиск основных зон

На столе определяются:

```text
TABLE
CHAT
NICK
STACK
BOARD
SHOWDOWN
```

Например:

```text
TABLE 5
 ├── CHAT ROI
 ├── SEAT 1
 │    ├── NICK ROI
 │    └── STACK ROI
 ├── SEAT 2
 │    ├── NICK ROI
 │    └── STACK ROI
 ...
 ├── BOARD ROI
 └── SHOWDOWN ROI
```

---

# 4. YOLO как сегментатор строки чата

Это важная часть новой идеи.

Допустим, чат содержит:

```text
gosumax ставит большой блаинд 300
```

YOLO получает **кроп строки**, а не пытается распознать сам текст.

Он должен разделить строку на смысловые сегменты:

```text
┌────────┐ ┌──────────────────────────┐ ┌─────┐
│gosumax │ │ ставит большой блаинд    │ │ 300 │
└────────┘ └──────────────────────────┘ └─────┘
   NICK              TECH                  VALUE
```

То есть результат YOLO:

```text
NICK
TECHNICAL
VALUE
```

с координатами каждого сегмента.

Например:

```text
NICK       → x1,y1,x2,y2
TECHNICAL  → x1,y1,x2,y2
VALUE      → x1,y1,x2,y2
```

После этого создаются **три отдельных crop**.

---

# 5. OCR после YOLO-сегментации

Каждый сегмент отправляется своему распознавателю.

## NICK

```text
NICK crop
   ↓
PARSeq
   ↓
gosumax
```

## TECHNICAL

```text
TECHNICAL crop
   ↓
Tesseract
   ↓
ставит большой блаинд
```

## VALUE

```text
VALUE crop
   ↓
Tesseract
   ↓
300
```

То есть YOLO отвечает:

> где находится нужная часть?

PARSeq/Tesseract отвечает:

> что именно там написано?

---

# 6. Start Stack

Для стартовых стеков:

```text
START STACK ROI
       ↓
upscale ×2
       ↓
Tesseract
       ↓
amount
       ↓
confidence %
```

Стартовый стек должен быть отдельным типом данных и не смешиваться с обычным OCR чата.

---

# 7. Chat Engine

Чат необходимо рассматривать как отдельный поток.

На каждом столе:

```text
CHAT
 ↓
10–30 line ROI
```

Каждая строка получает собственный ID.

Например:

```text
line_id = 157
```

У строки сохраняется:

```text
line_id
first_frame
last_frame
ROI
position
status
```

---

# 8. Почему ID строки нельзя делать только через OCR

OCR может ошибиться:

```text
gosumax
gosumax
gosumax
gosumax
```

но иногда дать:

```text
gosumax
gosurnax
gosumax
```

Если строить ID только по OCR, одна и та же строка может ошибочно превратиться в несколько строк.

Поэтому:

**ID строки должен определяться визуальным объектом/положением строки, а OCR используется для содержания.**

Для этого используем OpenCV tracking.

---

# 9. OpenCV используется для tracking

После того как YOLO нашёл строку:

```text
YOLO
 ↓
line ROI
 ↓
OpenCV tracker
```

OpenCV отслеживает строку между кадрами.

Например:

```text
frame 10000 → line 157
frame 10001 → line 157
frame 10002 → line 157
frame 10003 → line 157
...
```

Пока строка не изменилась:

**OCR повторно не запускается.**

---

# 10. YOLO не нужно запускать на каждом кадре

Это принципиально.

YOLO работает как:

> поиск / сегментация / восстановление.

OpenCV работает как:

> дешёвое сопровождение уже найденного объекта.

Пример:

```text
frame 10000
    ↓
YOLO нашёл CHAT LINE 157
    ↓
OpenCV tracking
    ↓
10001
10002
10003
10004
...
```

Если OpenCV продолжает уверенно отслеживать объект — YOLO не нужен.

Если tracking потерял объект или появились изменения структуры:

```text
OpenCV потерял ROI
       ↓
YOLO повторный поиск
       ↓
новый ROI
       ↓
OpenCV снова tracking
```

Таким образом YOLO не становится узким местом на каждом кадре.

---

# 11. Изменение строки запускает OCR

Главная оптимизация:

```text
строка не изменилась
        ↓
ничего не делаем
```

Если строка изменилась:

```text
изменение
 ↓
новый crop
 ↓
YOLO segmentation
 ↓
NICK / TECH / VALUE
 ↓
OCR
```

То есть OCR работает по событиям, а не по каждому кадру.

---

# 12. Пример обработки строки

Исходная строка:

```text
Дилер gosumax ставит большой блаинд 1400
```

YOLO должен определить смысловые сегменты.

Например:

```text
SYSTEM / TECHNICAL
NICK
TECHNICAL
VALUE
```

После обработки:

```text
игрок:
gosumax

технические слова:
ставит большой блаинд

сумма:
1400
```

Для другой строки:

```text
gosumax ставит анте 350
```

результат:

```text
игрок = gosumax
technical_words = ставит анте
amount = 350
```

---

# 13. Технический словарь

После OCR существует отдельная колонка:

```text
тех слова
```

Она **не должна сразу превращаться в нормализованное событие**.

Сначала сохраняем оригинальный OCR:

```text
ставит большой блаинд
```

Затем отдельный technical-term dictionary определяет:

```text
ставит большой блаинд
        ↓
BIG_BLIND
```

или:

```text
ставит анте
        ↓
ANTE
```

Это позволяет отдельно улучшать словарь, не переделывая OCR.

---

# 14. Board cards

Карты борда имеют собственный ROI:

```text
BOARD ROI
 ↓
card crops
 ↓
card recognition
```

Например:

```text
Ah
Kd
7c
```

Они не должны распознаваться как обычный OCR текста чата.

---

# 15. Showdown cards

Карты игроков на showdown тоже имеют собственные ROI:

```text
SHOWDOWN
 ↓
player card ROI
 ↓
card recognition
```

Например:

```text
playa_btw показывает комбинацию
Пара
JJ
```

Карты:

```text
JJ
```

хранятся отдельно от обычного OCR текста.

---

# 16. Общая структура строки данных

Базовые колонки Excel:

```text
номер кадра
время
номер раздачи
источник
категория
событие
игрок
сумма
тех слова
карты
место
подробности
текст окр
```

Дополнительно необходимо добавить:

```text
ocr_engine
confidence
```

или, лучше, отдельные confidence:

```text
player_confidence
technical_confidence
amount_confidence
card_confidence
row_confidence
```

Потому что одна строка может иметь:

```text
PARSeq = 98%
Tesseract technical = 96%
Tesseract amount = 73%
```

И общий confidence не должен скрывать проблему суммы.

# 18. Confidence и повторное распознавание

Для Tesseract и PARSeq сохраняем confidence в процентах.

Например:

```text
gosumax → 97%
ставит анте → 94%
350 → 72%
```

Если confidence высокий:

```text
≥ 95%
```

можно принимать результат.

Если ниже порога:

```text
< 90%
```

запускается повторная проверка соседних кадров.

---

# 19. Повторная проверка по 6 соседним кадрам

Для плохого результата нужно посмотреть соседние кадры.

Идея:

```text
        текущий
           ↓
-3  -2  -1  0  +1  +2  +3
```

То есть всего **7 кадров вместе с текущим**.

Вместо того чтобы склеивать их в одну картинку, лучше:

```text
crop -3 → OCR
crop -2 → OCR
crop -1 → OCR
crop  0 → OCR
crop +1 → OCR
crop +2 → OCR
crop +3 → OCR
```

Затем сравнить результаты.

Например:

```text
frame -3 → 350
frame -2 → 350
frame -1 → 350
frame  0 → 350
frame +1 → 350
frame +2 → 35O
frame +3 → 350
```

Очевидный результат:

```text
350
```

Это можно сделать через temporal consensus / voting.

---

# 20. Важный момент по повторному OCR

Не надо автоматически делать 7 OCR для каждого текста.

Иначе мы снова создадим огромную нагрузку.

Поэтому принцип:

```text
confidence >= 95%
        ↓
принять

90–95%
        ↓
небольшая проверка / при необходимости

<90%
        ↓
neighbor-frame retry

если результат стабилен
        ↓
принять

если результаты расходятся
        ↓
UNRESOLVED
```

Конкретные пороги можно отдельно протестировать на реальном видео.

# 24. Главный принцип новой архитектуры

Нельзя делать:

```text
каждый кадр
 ↓
YOLO
 ↓
OCR всего
 ↓
Excel
```

Нужно делать:

```text
кадр
 ↓
дешёвый tracking
 ↓
есть изменение?
 ├── НЕТ → ничего
 │
 └── ДА
      ↓
   YOLO
      ↓
   сегментация
      ↓
   нужные crop
      ↓
   специализированный OCR
      ↓
   confidence
      ↓
   при плохом confidence → соседние кадры
      ↓
   technical dictionary
      ↓
   event
      ↓
   hand state
```

---

# 25. Главная идея связки YOLO + OpenCV

**YOLO:**

* находит;
* сегментирует;
* определяет классы;
* восстанавливает потерянные ROI.

**OpenCV:**

* трекает уже найденные ROI;
* работает между YOLO;
* дешёво отслеживает строки;
* помогает понять, что ROI всё ещё тот же;
* позволяет не запускать YOLO на каждом кадре.

**PARSeq:**

* читает ники.

**Tesseract:**

* читает суммы;
* технические слова;
* стартовые стеки;
* другие обычные текстовые сегменты.

**Card recognition:**

* читает карты отдельно.

**Technical dictionary:**

* переводит OCR технических слов в нормализованные события.

**Hand State:**

* собирает события в полноценную раздачу.

---

# 26. Почему эта архитектура подходит для realtime

Главное — разделить:

```text
SOURCE
```

и

```text
PARSER
```

Сегодня:

```text
MP4
 ↓
frames
 ↓
parser
```

В будущем:

```text
RTSP / capture / stream
 ↓
frames
 ↓
тот же parser
```

Внутренняя логика не должна знать, откуда пришёл кадр.

---

# 27. Что пока НЕ фиксируем

Есть вещи, которые надо проверить экспериментом:

1. Какой именно OpenCV tracker лучше для наших строк.
2. Нужно ли использовать optical flow или template matching.
3. Как часто делать контрольный YOLO.
4. Как именно обучать YOLO на NICK / TECHNICAL / VALUE.
5. Нужна ли именно segmentation-модель или обычных bounding boxes достаточно.
6. Оптимальный confidence threshold.
7. Какой алгоритм temporal consensus лучше.
8. Как обрабатывать конфликтующие OCR-результаты.
9. Нужно ли повторять YOLO при каждом новом chat line или только при потере tracking.
10. Какова реальная скорость такой схемы на 9 столах.

Это нужно измерить на реальном видео, а не предполагать заранее.

# Итоговая схема

```text
                    VIDEO / REALTIME
                           │
                           ▼
                     9 TABLE SPLITTER
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       TABLE 1          TABLE 2          TABLE 9
          │                │                │
          └────────────────┼────────────────┘
                           │
                     YOLO DETECTION
                           │
       ┌───────────┬───────┼────────┬───────────┐
       ▼           ▼       ▼        ▼           ▼
     CHAT        NICK    STACK    BOARD      SHOWDOWN
       │           │       │        │           │
       │           │       │        │           │
       ▼           ▼       ▼        ▼           ▼
    OpenCV       PARSeq  Tesseract Cards      Cards
    tracking               ×2
       │
       ▼
  CHAT LINE CHANGE?
       │
       ├── NO → tracking
       │
       └── YES
             │
             ▼
       YOLO SEGMENTATION
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
     NICK   TECH  VALUE
       │     │     │
     PARSeq Tesseract
             │
             ▼
          CONFIDENCE
             │
       < 90% → соседние
             │     кадры
             ▼
       TEMPORAL CONSENSUS
             │
             ▼
      TECHNICAL DICTIONARY
             │
             ▼
       EVENT NORMALIZER
             │
             ▼
         HAND STATE
             │
             ▼
        HAND RECORD
             │
        ┌────┴────┐
        ▼         ▼
      EXCEL       DB
```

**Ключевая новая идея:** YOLO используется как **структурный сегментатор текста**, а не как OCR. Он превращает строку вроде `gosumax ставит большой блаинд 300` в три смысловых crop: **NICK + TECHNICAL + VALUE**. OpenCV при этом занимается дешёвым tracking этих объектов между кадрами. Это позволяет не гонять тяжёлые YOLO и OCR на каждом кадре.
