# Независимая оценка плана нового парсера

Дата: 27 сентября 2026. Это архитектурная оценка и передача контекста, не реализация и не новый прогон моделей.

План имеет хорошую основу: независимый источник кадров, отдельное состояние столов, OCR по изменениям, специализированные распознаватели, сохранение raw OCR и отдельная нормализация. Но его пока нельзя считать готовой архитектурой полного HH: пропуски наблюдений, переносы сообщений, идентичность объектов, START и финализация требуют явных правил. Основной риск — потерять событие или неправильно связать его с рукой, даже при хорошем OCR.

## Какие изменения я предлагаю

1. N столов, а не жёстко 9. Один декодер источника, реестр table_session_id, отдельный порядок событий каждого стола и общий ограниченный пул OCR. Новое окно в старом экранном слоте должно начинать новую сессию.
2. Для чата сначала оценивать общий вертикальный сдвиг и сопоставлять последовательность строк с перекрытием. Отдельный универсальный tracker на каждую строку — кандидат для теста, не обязательный фундамент. Одинаковые тексты могут быть разными событиями; hash нужен для кэша, но не как единственный event_id. Координата экрана тоже не ID.
3. Разделить physical_row_id, message_id и event_id. Перенесённая сумма, продолжение all-in, выигрыш из нескольких банков и комбинация могут занимать несколько физических строк. Собирать сообщение с provenance каждого фрагмента, не дописывать невидимое.
4. NICK/TECH/VALUE оставить как первый эксперимент, но выход сделать списком 0..N сегментов. Есть SYSTEM, HAND_NUMBER, CARD_TEXT, SEAT, несколько сумм и отсутствие ника. Роль числа определяется контекстом: ставка, raise-to, возврат, банк, награда. Сам детектор не гарантирует понимания смысла.
5. Для прямоугольных текстовых кропов начать с bounding boxes, а не масок. Сравнить YOLO-поля с дешёвой геометрией/границами слов на одном тесте. Выбирать по точности итоговых полей и стоимости всей цепочки. Detection выдаёт рамки, segmentation добавляет маски: https://docs.ultralytics.com/tasks/segment/
6. Confidence движков хранить как raw_score с engine/version; это не готовая вероятность правильности. Пороги калибровать отдельно для ника, суммы и карт по независимым данным. Согласованная ошибка на семи одинаковых кадрах остаётся ошибкой.
7. Повторный OCR выбирать по качеству и различию наблюдений одного и того же объекта. Не брать слепо ±3 кадра: там могут быть другой стек, прокрутка или другая рука. В realtime будущие кадры потребуют задержки и ring buffer; ограничить окно и число повторов, сохранить UNRESOLVED.
8. OCR по изменениям дополнить контрольной переоценкой и попыткой на лучшем кадре. Если строка не изменилась, но первый кроп был обрезан или размыт, запрет повторного OCR помешает исправлению. При переполнении буфера фиксировать GAP; исчезнувшую между захватами строку восстановить из ничего нельзя.
9. Стартовый стек — фазовый факт. Хранить observed_stack с временем, а pre_forced_stack отдельно и только при доказательстве фазы/удержаний. Чтение Tesseract x2 само по себе не определяет START. Добавить dealer button, seat identity, occupancy/sitout и границы рук.
10. Между observation и hand state нужен долговечный журнал. Сохранять PNG/hash, source_id, PTS/frame, table_session_id, ROI/transform, row/message IDs, raw OCR, модель, варианты, причины отказа. Нормализованные события версионировать; повторный запуск не создаёт дублей. Excel — экспорт. Для первого варианта достаточно SQLite и файлов кропов, внешний брокер заранее не нужен.
11. HAND STATE должен различать порядок наблюдений и время действий, raise-to и добавленную сумму, all-in, uncalled return, side pots, split pots, конец записи и неполную руку. Валидатор денег/карт проверяет результат, но не выдумывает пропуски. JJ без мастей — не две полностью известные карты.
12. Разделить черновую руку, полную проверенную руку и экспорт. EOF или завершённый OCR не означает готовый HH. Сохранять явные причины PARTIAL/UNKNOWN.

## Предлагаемая цепочка

Source adapter → Frame + PTS → bounded ring buffer → Table registry → visual observations / chat alignment → physical rows → message assembly → field crops → OCR/card reader → durable evidence journal → normalized event revisions → hand reducer → validators → HH/Excel export.

Для независимых визуальных событий BOARD/STACK/POT путь не обязан проходить через сборщик chat messages. У каждого стола свой порядок, а вычислительные ресурсы общие. При нехватке ресурсов допускается снижать частоту повторных неизменных наблюдений, но нельзя молча терять изменения чата.

## Что обучать и в каком порядке

A. Обязательное новое обучение при выборе предложенного YOLO-подхода: детектор полей сообщения. Сначала схема разметки, примеры переносов и несколько чисел; затем разметка по пикселям. Каталог сущностей использовать для поиска примеров, не как автоматически истинные labels.
B. Дообучение имеющегося board detector на закрытой пятой карте, анимациях и других подтверждённых ошибках — после отдельного контрольного набора.
C. PARSeq на реальных никах: сначала независимый benchmark, проверка charset и длины, затем fine-tune по ошибкам. Готовый PARSeq и настройка charset описаны в первичном репозитории: https://github.com/baudm/parseq . Не отправлять в латинский nickname-reader русскую строку целиком.
D. Card rank/suit reader: если существующий не проходит тест, отдельное обучение/калибровка для board и shown crops, включая неизвестные/обрезанные карты.
E. Универсальные NICK/STACK/button/pot/seat detectors и расширение table detector — условно, по провалам геометрии и новым layouts. Не все зоны обязаны быть отдельными нейросетями.

## Первые проверяемые этапы

1. Зафиксировать реестр моделей: файл, SHA-256, классы, разрешения, данные обучения, holdout, ограничения. Ничего не переобучать вслепую.
2. Подготовить независимый небольшой, но разнообразный тест полных сообщений и последовательностей: обычные, переносы, одинаковые строки подряд, крупный скролл, закрытие/смена стола, START, showdown. Делить train/val/test по видео/сессиям; соседние почти одинаковые кадры не разносить между ними. Старые holdout, по которым уже выбирали версии и пороги, не считать финальным независимым тестом.
3. Собрать один стол до доказуемого журнала: пропуски/дубликаты, точные nickname/amount/action, provenance. Затем полный HH с валидаторами.
4. Сравнить способы выделения полей и распознаватели. Считать exact-event и exact-hand, а не только mAP/CER.
5. Масштабировать на девять столов. Измерять wall time/video time, p95 задержки, очередь, RAM/VRAM, число OCR и потери; без измерения не обещать realtime.
