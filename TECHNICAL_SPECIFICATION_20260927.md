# Техническое задание: новый парсер PokerDom

Версия: 1.1. Дата: 27.09.2026. Учтены найденные материалы прошлой задачи о сегментации событий и сущностях чата.

Статус: спецификация для разработки и согласования критериев производительности. Создание этого документа не означает запуск реализации или обучения.

## 1. Цель и границы

Разработать парсер PokerDom, который извлекает из видео наблюдения, собирает события отдельных столов и формирует проверяемые истории раздач (HH). Любое опубликованное поле должно иметь связь с исходным изображением и результатом распознавания.

Первый источник — записанное видео. Архитектура должна поддерживать последующее подключение realtime-захвата без изменения логики распознавания и сборки рук. Целевая нагрузка — девять одновременно видимых столов; количество столов задаётся конфигурацией.

Первая реализация работает с согласованными раскладками PokerDom. Поддержка неизвестного масштаба, темы или расположения окон подтверждается отдельной проверкой, а не предполагается автоматически.

В объём входят: захват, обнаружение столов, чат, игроки и места, стеки, обязательные взносы, действия, борд, открытые карты, банк, сборка и проверка рук, экспорт и диагностические отчёты. Интерфейс для игры, принятие игровых решений и управление клиентом не входят в объём.

## 3. Основные требования

1. Сохранять исходные изображения, raw OCR, альтернативы и причины отказа.
2. Не превращать отсутствие доказательств в известный факт. Использовать `UNKNOWN`, `UNRESOLVED`, `PARTIAL` и явные причины.
3. Отделять наблюдение от интерпретации: увиденная сумма стека не является автоматически стартовым стеком.
4. Сохранять порядок событий внутри каждого стола независимо от порядка завершения OCR-задач.
5. Повторная обработка и восстановление после сбоя не создают дубликатов событий и экспортов.
6. Проверки денег и карт выявляют ошибки; они не дописывают пропущенные действия и не заменяют исходный OCR.
7. Завершение файла, OCR или процесса не означает готовность полного HH.

## 4. Архитектура

```text
Source adapter → Frame + PTS → bounded buffer → Table registry
                                                    │
                    ┌───────────────────────────────┴──────────────────┐
                    ▼                                                  ▼
          Chat alignment / physical rows                Seat / stack / button /
                    ↓                                   board / shown / pot
          Message assembly                                         ↓
                    ↓                                    Visual field readers
          Field extraction → OCR                                   │
                    └───────────────────────┬────────────────────────┘
                                            ↓
                             Durable evidence and result journal
                                            ↓
                              Versioned normalized events
                                            ↓
                                  Per-table hand reducer
                                            ↓
                                  Validators → exports
```

Исходные наблюдения записываются в журнал до нормализации; схема показывает общий путь данных, а не разрешение откладывать сохранение доказательств до конца OCR.

Для первой версии использовать SQLite и файлы кропов. Запись в БД централизованная и транзакционная. Внешний брокер сообщений не требуется. У столов отдельное логическое состояние, но общий ограниченный пул OCR и нейросетевого inference. Число процессов не обязано совпадать с числом столов.

### 4.1. Источник и буфер

- Единый контракт кадра: `source_id`, `frame_id`, `source_pts`, `capture_time`, изображение, размеры, состояние источника. Для файла `capture_time` может отсутствовать.
- Время видео брать из временных меток источника; не предполагать постоянный FPS.
- Один декодер обслуживает все столы одного источника.
- Размер буфера, глубина очередей и число повторов ограничиваются конфигурацией.
- Для файла при перегрузке обработка замедляется без молчаливого пропуска кадров. Для realtime регистрируются потерянные интервалы `GAP` с причиной и затронутыми столами.
- MP4 может повторно читать прошлые кадры. Realtime использует только сохранённый буфер; ожидание будущего кадра имеет ограниченный срок.

### 4.2. Реестр столов

- Создавать устойчивый `table_session_id`, хранить геометрию и преобразования координат.
- Перемещение существующего окна не должно автоматически создавать новый стол.
- Замена стола в прежнем слоте должна создавать новую сессию. При недостатке доказательств связь сессий остаётся неопределённой.
- Обнаруживать исчезновение, перекрытие и изменение масштаба. Скрытый чат не должен сам по себе доказывать отсутствие стола.
- Для поддерживаемых раскладок допустима нормализованная геометрия ROI; универсальный детектор всех зон не является обязательным.

### 4.3. Чат и идентичность сообщений

- Основной кандидат: оценка общего вертикального сдвига и сопоставление последовательностей строк с перекрытием.
- Индивидуальные trackers, optical flow и template matching сравнивать на одинаковых последовательностях; не закреплять алгоритм до проверки.
- Разделять `physical_row_id`, `message_id`, `event_id`.
- Пиксельный хеш применять для кэша; одинаковые изображения или тексты не являются достаточным основанием объединять события.
- Собирать сообщения из нескольких физических строк с provenance каждого фрагмента.
- Поддерживать одинаковые сообщения подряд, частично обрезанные строки, перенос суммы, all-in, описания комбинации и выплаты из нескольких банков.
- После резкого скролла увеличивать плотность анализа доступных кадров. Если непрерывность не доказана, сохранять разрыв или неопределённость, не выдумывать недостающие строки.
- Первая видимая строка записи может быть продолжением сообщения; это отражается в статусе.

### 4.4. Выделение полей и распознавание

Сравнить три варианта: OCR сообщения целиком с разбором; геометрическое выделение полей; обученный детектор рамок полей. Основной критерий — точность итогового события с учётом стоимости всей цепочки.

Выход выделения полей: упорядоченный список из нуля или более сегментов. Предварительные визуальные классы: `NICK`, `TECH`, `VALUE`, `SYSTEM`, `HAND_NUMBER`, `SEAT`, `CARD_TEXT`. Они не заменяют готовый семантический каталог из раздела 13: несколько смысловых типов могут иметь общий визуальный класс. Окончательная схема рамок и таблица соответствия семантическим типам фиксируются до разметки. Роль числа определяется нормализатором по контексту сообщения.

- Для YOLO-полей начинать с bounding boxes. Маски вводить только при измеренном преимуществе.
- PARSeq рассматривается как кандидат для ников, Tesseract — для чисел и технического текста. Выбор движка для каждого поля подтверждается сравнением.
- Хранить исходный текст, движок, версию модели, preprocessing, raw score и альтернативные чтения.
- Raw score не маркировать как вероятность правильности. Пороги принятия калибровать отдельно по полям на независимой выборке.
- OCR запускается для новых полей, изменившихся наблюдений и ограниченных повторов неразрешённых результатов.
- Повторы выбирать по качеству и различию кропов одного объекта. Фиксированное голосование по ±3 кадрам не является обязательным алгоритмом.
- Не объединять чтения разных фаз стека, рук или сообщений. Повтор одинаковой ошибки не считается независимым подтверждением.
- Изменение словаря нормализации не требует повторного OCR сохранённых данных.

### 4.5. Визуальные факты

- Ники мест, занятость, sitout, button, стеки, board, shown cards и pot обрабатываются отдельными наблюдениями.
- Для стека хранить сумму, единицу отображения, место, время и доказанную фазу. `observed_stack` и `pre_forced_stack` — разные поля.
- Стек до обязательных взносов устанавливать только при подтверждённой фазе или полностью подтверждённых удержаниях с сохранением основания вывода.
- Различать пустое место, временно закрытый ROI и нераспознанное содержимое.
- Наличие карты и её rank/suit — разные задачи. Для каждой карты поддерживать частично известное и неизвестное значение.
- `JJ` без мастей не преобразовывать в две полностью известные карты.
- Борд и карты игроков не проводить через обычный OCR технических слов. Текст карт в чате сохраняется отдельным источником.
- Наблюдаемый банк использовать для независимой проверки с учётом момента обновления интерфейса. Несовпадение сохранять, а не исправлять им действия.

## 5. Контракты данных

| Сущность | Обязательные данные |
|---|---|
| Observation | ID, source/frame/PTS, table_session_id, тип ROI, координаты и transform, путь и hash кропа, качество, статус |
| PhysicalRow | ID, chat epoch, первое/последнее наблюдение, связанные Observation, состояние сопоставления |
| Message | ID, упорядоченные фрагменты строк, признаки начала/окончания, полнота, ссылки на доказательства |
| Recognition | ID наблюдения/поля, raw text, engine/model/version, preprocessing, raw score, альтернативы, статус |
| EventRevision | стабильный event_id, revision, ссылки на Message/Observation, тип, actor/seat, amount и его смысл, cards, порядок, статус, версия нормализатора |
| HandRevision | hand/session ID, границы, версии событий, начальное состояние, действия, board, выплаты, ошибки проверок, статус |
| Export | hand revision, формат, версия экспортера, hash результата, время, статус и причина отказа |

Общие правила:

- Денежные значения хранить точно: целыми минимальными единицами либо decimal; единица обязательна. Не использовать binary float для расчёта банка.
- Хранить отдельно время наблюдения и известное время действия. Появление текста в кадре не доказывает точное время действия.
- К каждому производному факту прикладывать основания и версию преобразования.
- Исправление распознавания создаёт новую версию; исходное наблюдение и прежний результат сохраняются.
- Ключ идемпотентности основан на идентичности источника/наблюдения и операции, а не только на тексте.

## 6. Сборка и проверка раздач

Сборщик должен поддерживать границы рук, игроков и места, обязательные взносы, fold/check/call/bet/raise, all-in, улицы, showdown/muck, uncalled return, основной и побочные банки, раздел банка и выплаты.

Различать итоговую величину рейза (`raise_to`) и добавленную сумму. Не подменять пропущенное действие арифметически подходящим действием.

Проверки: допустимость последовательности, принадлежность игрока месту и руке, баланс вложений/возвратов/выплат с учётом подтверждённых правил игры, уникальность известных карт, соответствие улиц и борда, согласованность независимых источников. Рейк или иные удержания не выдумывать для закрытия баланса.

Статусы:

- `DRAFT` — ожидаются данные или завершение обработки.
- `PARTIAL` — часть обязательных фактов отсутствует или не разрешена; причины перечислены.
- `REJECTED` — доказанное противоречие не позволяет принять руку.
- `VERIFIED` — обязательные для выбранного формата факты подтверждены, проверки пройдены, входные события финализированы.

Полный HH экспортируется только из текущей `VERIFIED`-версии. Частичные руки доступны в диагностическом экспорте с явным статусом. Новое существенное доказательство пересматривает руку и делает устаревший экспорт неактуальным. EOF закрывает источник, но не повышает статус руки.

## 8. Данные и независимая проверка

- Разметку эталона выполнять по исходным изображениям и последовательностям. OCR-подсказки и прежний Excel не принимать за независимую истину.
- Нечитаемые примеры помечать `AMBIGUOUS`; не придумывать правильный текст.
- Разделять train/validation/test по видео или сессиям. Исключать соседние почти одинаковые кадры между выборками.
- Наборы, использованные для выбора моделей и порогов, не объявлять финальным независимым тестом.
- В эталон включать обычные сообщения, переносы, несколько чисел, одинаковые сообщения подряд, крупные прокрутки, обрезанные строки, смену/перемещение стола, START, all-in, возврат, side/split pots, showdown и обрыв записи.
- Отсутствующий в корпусе сценарий помечать `NOT_TESTED`; не включать его в подтверждённый объём поддержки.

Начальный объём для этапа 1: не менее 300 полных сообщений из нескольких независимых последовательностей, не менее 30 трудных переходов чата и не менее 10 полных рук. Это минимальный инженерный набор, не доказательство качества на всех видео. Каждый обязательный сценарий должен иметь проверяемый пример либо явный статус отсутствия покрытия.

Метрики: пропуски/дубликаты строк, сообщений и событий; ошибки порядка и привязки; exact nickname/action/amount/cards; exact event; exact hand; доля unresolved; доля ошибочно принятых результатов. Все метрики публиковать с числителем, знаменателем и разбивкой по сценариям. CER и mAP — вспомогательные показатели.

## 9. Производительность и восстановление

- Измерять полное время от чтения источника до сохранённого результата, а также стоимость этапов.
- Публиковать wall time / video duration, throughput, p50/p95 задержки, RAM/VRAM, глубину очередей, число запусков OCR/моделей, повторы и потери.
- Для девяти столов считать время всего исходного видео, а не сумму длительностей кропов столов.
- Записывать оборудование, версии, разрешение/FPS источника, число столов и режим кэша.
- Цель realtime: wall time / video duration ≤ 1 при ограниченной очереди на выбранном оборудовании. Допустимая p95 задержка, RAM/VRAM и длительность нагрузочного теста фиксируются до этапа масштабирования. До этого realtime считается неподтверждённым.
- После принудительного завершения процесса восстанавливать обработку из журнала. На контрольном наборе результат после восстановления должен семантически совпадать с непрерывным запуском; служебные времена могут различаться.
- Контролировать повторную доставку результатов, сбой OCR, отсутствие модели, потерю кадров и переполнение очереди. Ни один из этих случаев не должен давать ложный `VERIFIED`.

## 10. Этапы и условия приёмки

### Этап 0. Инвентаризация и фиксация контрактов

Результат: реестр моделей с hash, перечень переиспользуемых модулей, поддерживаемые раскладки, схема данных, спецификация разметки и протокол теста. Зафиксировать целевой формат HH и версию программы-потребителя, если требуется совместимость.

Приёмка: назначение каждой модели подтверждено её интерфейсом; неизвестные возможности явно обозначены; старые проекты не изменены.

### Этап 1. Один стол: доказуемый журнал

Результат: полный путь кадр → строки → сообщения → поля → события с доступными кропами и отчётом ошибок.

Приёмка на замороженном эталоне:

- Все размеченные видимые сообщения представлены результатом или явной зарегистрированной неопределённостью/потерей. Молчаливых пропусков нет.
- Нет дубликатов и неверного порядка среди принятых событий.
- Каждое принятое поле имеет ссылку на доказательство; неизвестные поля сохранены явно.
- Повторный запуск не создаёт дополнительных логических событий.
- Отчёт показывает и точность, и долю unresolved; результат «всё UNKNOWN» не считается успешным распознаванием.

Для эталона с однозначно читаемыми и полными исходными данными требуется точное восстановление всех размеченных событий. Непрохождение показывает конкретный блокирующий сценарий, а не допускает снижение требований молча.

### Этап 2. Выбор распознавателей и обучение полей при необходимости

Результат: сравнение вариантов выделения полей на одинаковых данных, выбранная конфигурация, при необходимости новые веса и их паспорта.

Приёмка: выбор обоснован exact-event, ошибочно принятыми полями, unresolved и полной стоимостью обработки. Улучшение CER/mAP без улучшения конечных полей недостаточно. Тестовые данные не использованы для обучения и настройки порогов.

### Этап 3. Полные истории рук

Результат: сборщик рук, денежные/карточные проверки, HH и диагностический экспорт.

Приёмка: все полностью наблюдаемые и однозначно размеченные руки контрольного набора точно восстановлены; неполные и противоречивые примеры не опубликованы как полные. Импорт в выбранную программу проверяется, если он входит в согласованный формат поставки.

### Этап 4. Девять столов и подготовка realtime

Результат: общий планировщик, измерения нагрузки, восстановление и испытание realtime-адаптера либо его тестового эмулятора с ограниченным буфером.

Приёмка: качество по столам сохраняется относительно одностольной обработки; результаты не смешиваются; память и очереди ограничены; потери зарегистрированы; выполнены заранее зафиксированные бюджеты скорости и задержки. Проверка файла без ограничения буфера не заменяет realtime-испытание.

Полный журнал является источником данных; Excel — его представлением.

### 13.4. Переход от каталога к обучающей разметке

1. Сохранить неизменяемый манифест выбранных исходных записей, файлов и hash; старые выгрузки не редактировать.
2. По ссылкам восстановить исходные PNG и контекст соседних строк/кадров.
3. Визуально проверить текст, тип, принадлежность сообщению и полноту. Непроверенные метки из OCR не использовать как эталон теста.
4. Разметить пиксельные рамки полей с размерами исходного изображения. `text_start/text_end` сохранить только как текстовые позиции.
5. Для многострочных сущностей хранить несколько рамок и общий entity/message ID; не включать в единственную широкую рамку чужие строки.
6. Различать visual class и semantic type. `SYSTEM_MESSAGE` может охватывать `HAND_NUMBER` или `BLIND_LEVEL`; вложенность семантики не требует дублировать всю строку в нескольких визуальных классах.
7. Хранить `entity_id`, `message_id`, `semantic_type`, `role`, `raw_text`, `text_span`, `bbox_refs`, `parent_entity_id`, `evidence_status`, `annotation_version` и сведения о проверке.
8. Разделить данные по независимым сессиям до обучения. Примеры, использованные при разработке каталогов и правил, считать материалом разработки, а не автоматически независимым финальным тестом.

Приёмка этапа 0 дополнительно требует таблицу покрытия всех перечисленных типов: источник примеров, статус проверки, visual class, способ чтения, правило сборки/нормализации и наличие независимого теста. Разработчик должен расширять найденные каталоги, а не начинать перечень сущностей заново.
